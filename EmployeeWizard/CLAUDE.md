# EmployeeWizard — Tool Context

## What This Tool Does

EmployeeWizard is an **employee roster, work-schedule, and labour-cost tracking** tool for licensed cannabis cultivation facilities. It manages who works which days of the week, books employee time off as shared calendar events, records daily labour hours against lot tasks (generated by Labour wizards), and produces labour cost reports normalized per plant.

### Intended Use

- **Manage the employee roster:** Add, edit, and delete employees with a name, an optional hourly wage (no default — never a made-up figure), and an ongoing work week (which of the 7 days they work).
- **Book time off:** Create book-off events per employee — multi-day or partial — that become shared calendar events. Ongoing shifts do **not** create calendar events; only booked time off does.
- **Track labour on tasks:** For a selected lot, browse the tasks generated by any Labour wizard (currently `CropLabourWizard`; more may come) in a terminal-style list and record daily hours per employee (or temp worker) into each task's `labour_map`. Mark tasks completed from the editor panel when finished.
- **Man-hour tracking:** How many people × how much pay × how many hours, per task, day to day. Averages time per plant on tasks to find averages for different size rooms.
- **Labour reports:** Per crop (total recorded), per day/week across all crops, per task (average across crops per plant / individual events), and any other report a director might want — with insightful graphs on cost per task and cost trends by crop, strain, or room. *(Phase 5 — the estimated-vs-actual table and the 📊 Reports tab are built; see "Reports Tab" below and `REPORTS.md`.)*

## UI Layout

The tool has **three main tabs — Employees, Tasks and 📊 Reports**. Employees and Tasks use a two-panel setup: a scrolling list on the left and an editor panel on the right. Reports is a full-width page of charts (see "Reports Tab"). Below all three (full width) sits the **Labour Report** section.

### Employees Tab

**Left panel — employee list:**
- Scrolling list of all employees.
- Each row has a little red ✕ to delete the employee, **after confirmation**.

**Right panel — two states:**

1. **No employee highlighted → Work Week calendar.** A 7-day work-week view showing, for each day of the week, the names of the employees working that specific day (based on their ongoing schedules). The week starts **Monday** (Mon–Sun columns) and shows the **current week only** — no week navigation.
2. **Employee highlighted → Employee editor:**
   - **Top:** 7 buttons in a row (one for each day of the week) that toggle **green** (works) / **red** (off) to set the days that employee is working, ongoing.
   - **Middle:** 2 fields — **Name** and **Wage** ($/hour; blank — placeholder "not set" — when the employee has no wage, and saving it blank leaves the wage unset or clears it). Wages are open information — no confirmation step.
   - **Bottom:** two buttons — **Save Changes** (to employee) and **Request Time Off**.

**Time-off view** (entered via "Request Time Off"):
- The panel switches to a calendar for creating book-off events. Events can be **multi-day or partial**.
- **Partial = hour-based entries:** a book-off records specific hours off per day (e.g., `8:00–12:00`), so a day can be partially booked off rather than all-or-nothing.
- The calendar shows the employee's regular days on, and booked-off days (with partial-day shading/indication).
- At the bottom: a list of this employee's time-off events, each with a little ✕ to delete it.
- Booked time off becomes a shared **calendar event** (`sourceTool: "EmployeeWizard"`). Ongoing shifts never create calendar events.

### Tasks Tab

**Left panel — task list (terminal-style):**
- Scrolling list of tasks related to the **selected lot**, read from `calendarEvents` where `lotId === selectedLot` and `sourceTool` is a Labour wizard (currently `CropLabourWizard`; more may be added in the future).
- The list **defaults to today**. Completed/old tasks are **not shown** unless a checkbox ("show old/completed tasks") is selected. When old tasks are shown, the list still defaults to "today" and you can scroll up to older tasks.

**Right panel — task editor (when a task is highlighted):**
- Assign employees to **today's** labour map, or modify previous days.
- For a day: either pick an **existing employee** from the roster and input a time in **hours and minutes**, or fill in a **"Temp employee"** field with a name and wage. Temp employees are assigned on the task by name, below where you would select a regular employee.
- **+ Add day picker:** single-day events often grow into multi-day work. A small calendar popover (opened from the Day section) lets you pick other days work happened on; picking a date creates that day in the task's `labour_map` and selects it for editing. Added days sit outside the event's own `date`/`endDate`, which are left untouched — the task keeps its original due state until marked completed. Extra days show an ✕ to remove them while they still have no labour entries.
- A control to mark the task **completed** from this panel when the task is finished.
- **Estimate:** when the task has a CropLabourWizard labour estimate (`estStaff` / `estMinutes` per day — root `CLAUDE.md` → "Event Contract"), the meta line shows `⏱ Est. 👥 8 × 8h/day ≈ 448.0 h` and the task total adds `· estimated 448h`. The estimate covers the event's own `[date, endDate]` days; extra days added with "+ Add day" don't change it.

### Labour Report Section (below both panels)

**Estimated vs. actual hours** (`renderLabourReport`) — done. Office only: hidden on building devices with the rest of the office work.
- **Scope:** the Active Lot, or every lot when none is selected (global report, design decision 9). The header shows "Lot LOT-001" or "All lots".
- **Tasks counted:** Labour-wizard events (`LABOUR_TOOLS`) with a lot that have an estimate or recorded hours. Projections aren't included. Filters:
  - **From / To** on the task's start `date`; blank means no limit.
  - **Completed tasks only** is on by default, because open tasks only have part of their hours recorded.
- **Group by:** Task (task-type registry order, i.e. recipe order), Lot (oldest first), Room, or Building.
  - The room is where the task happens, by CropLabourWizard's phase rules (`taskRoomId`): the event's `roomId`, else the lot's cloning / veg / flower room by `roomPhase`, then by task type, else the lot's only room.
  - Unresolved tasks go under "No room" / "No building".
- **Columns:**
  - **Tasks:** with "(N no est.)".
  - **Estimated:** `estStaff × estMinutes × event days ÷ 60`.
  - **Actual:** all `labour_map` hours, on every day.
  - **Difference:** actual − estimated, with %. Amber when over, green when under.
  - **Per plant:** actual minutes per plant, using the current `plantCount` of the lots that have one.
  - **Bar pair:** outline = estimated, filled = actual, scaled to the largest row.
  - A **Total** row closes the table.
- **Notes under the table:** tasks with no estimate count as actual only, and tasks with an estimate but no hours are counted. Both totals are listed.
- Hours only — no $ figures yet (wages stay out of reports per person; cost reports are later Phase 5 work).
- Redrawn with the task tab (`renderTasksTab`), so it follows every labour entry, completion, lot change and DB load/update.

### Reports Tab (📊, office only)

The full spec, the metric list, the definitions and the **harvest-log hook-up steps** are in `EmployeeWizard/REPORTS.md`. In short:

- **Pages:**
  - **Overview:** 8 KPI tiles and Needs attention.
  - **Crop Timeline:** the crop labour Gantt and the room schedule Gantt.
  - **Labour:** hours by task, over/under estimate with suggested estimates, labour mix, $ per gram by phase.
  - **Yield & Quality:** strain scorecard, potency/terpene strips, weight cascade, room trend.
  - **Rooms & Environment:** climate per lot and the pest heat map.
  - **Forecast:** labour demand vs roster capacity, and the 6-month harvest forecast.
  - **⚙️ Setup & data:** canopy sq ft, shift length, crop summaries with archive import, and the metric hook-up table.
- **Filters:** a filter row (period, building, flower room, strain, **Per** plant / sq ft / light / gram / total) scopes every page. Per light uses each flower room's light count from SitkaTools' Room Manager. Comparisons are always against the previous period of the same length.
- **🖨️ Board pack:** opens the report pages in a print-ready window (light theme, Letter landscape, a tick box per page).
- **What drives yield?** (Yield & Quality page): any per-crop measure against an outcome, with a fitted line and r.
- **Reads every tool's data, read-only** (user decision 2026-10-12): calendar events and `labour_map`, the roster, CropLabourWizard / CropProjection schedules and estimates, PaperWizard answers to questions tagged with a report metric (`question.metric`), DailyWizard chore lists. It writes only `_EmployeeWizard.crops` and `_EmployeeWizard.settings`.
- **Crop summaries** (`_EmployeeWizard.crops[lotId]`, saved from Setup & data or imported from `Archive/Lot-*.json`) keep closed-out lots in the trends for 36 months. A lot still in the DB always uses its live numbers.
- **Privacy:** no $ per person; $ only while Wages.json is open; $ hidden for groups of fewer than 3 people. Live lots use today's wages; closed lots use the cost frozen with their summary.
- **Redraws:** only while the tab is open — on tab switch, DB load, live update (not while a Setup input is being typed in) and Active Lot change. The Active Lot picks the lot for the Gantt and climate charts.
- **Charts:** hand-rolled SVG with one shared tooltip and a ⊞ Table twin on every card.

Still to come (REPORTS.md §9): a lab-results card if potency isn't on a controlled form, and a fuller data-health page.

## Data Model — Database Keys

All data lives in the shared `DB-YY-MM-DD.json` database. EmployeeWizard owns:

**Top-level key `_EmployeeWizard`:**
```json
"_EmployeeWizard": {
  "employees": {
    "<name>": {
      "wage": 20,
      "workDays": [1, 3, 5],
      "timeOff": []
    }
  },
  "crops": { "<lotId>": { "version": 1, "savedAt": "…", "…": "crop summary — schema in REPORTS.md §4" } },
  "settings": { "canopySqFt": { "<roomId>": 1150 }, "shiftHours": 8 },
  "cropCosts": { "<lotId>": { "cost": 20358.4, "missingHours": 0, "savedAt": "…" } }
}
```

- `crops` — saved crop summaries (Reports → Setup & data). They keep a closed-out lot in the report trends, hold hours per person but never wages, and are dropped after 36 months. Created on the first save.
- `settings` — report settings: canopy area per flower room, and the shift length used for roster capacity (default 8 h). Created on the first change.
- `cropCosts` — the labour cost frozen when a crop summary is saved with wages open. Closed-out lots use it, so later raises don't restate them. It's money, so SitkaTools' split keeps it in **Wages.json** (office only), not Main.json.
- `crops` and `settings` live in Main.json with the roster (the split keeps everything in `_EmployeeWizard` there except wages and `cropCosts`).

- `wage` — $/hour. **Secret wage:** stored in the main JSON DB but **not visible on any dash or report** as a per-person figure; used only for cost math. Wage can be changed at any time. **Optional, no default:** new employees get no `wage` key, and an employee whose wage is blank (e.g. split DB with `Wages.json` not opened) keeps none — the tool never invents one, so a missing wage never turns into a $ figure or a wage change SitkaTools can't save.
- `workDays` — ongoing work days of the week (weekday numbers follow `Date.getDay()`: `0`=Sun … `6`=Sat). The UI displays them Monday-first. **New employees default to Mon–Fri** (`[1, 2, 3, 4, 5]`).
- Employees are keyed by name in this map. **Duplicate names are prevented** — adding an employee whose name already exists is rejected (the name *is* the identity, and labour maps reference it).

**Time-off events** (stored per employee, and mirrored to `calendarEvents`):
```json
{ "id": "string", "date": "YYYY-MM-DD", "endDate": "YYYY-MM-DD | null", "hoursOff": [{ "date": "YYYY-MM-DD", "start": "HH:MM", "end": "HH:MM" }], "calEventId": "ev_…" }
```
- `hoursOff` is present only for **partial** book-offs — a list of hour ranges per day. A full-day book-off has no `hoursOff` entry for that day (the whole day counts as off).
- `calEventId` is the `id` of the mirrored calendar event. Deleting a booking removes exactly that event, so two blocks on the same day stay separate; records booked before `calEventId` existed fall back to title + dates (first match only), and failing that to an orphaned time-off event with the same dates — titled for a name no longer on the roster (a rename used to leave the old title) and not linked by any booking's `calEventId` — used only when exactly one fits. Deleting the employee removes their bookings' events by id and by that lookup, plus any event with their time-off title. Renaming an employee retitles their time-off events and links older records to their event by id. The lookup only changes the DB on the user's delete or rename, never on load or render.
Each booked time-off also creates a calendar event in `calendarEvents`:
- `title`: e.g., `"🏖️ Time Off — <Employee Name>"`
- `date`, and `endDate` only when multi-day (suite convention: omit when equal to `date`)
- `sourceTool: "EmployeeWizard"`
- No `lotId` — time off is not lot-scoped.

**Task labour map (annotation on Labour-wizard events):**
Tasks are calendar events created by Labour wizards. EmployeeWizard adds a `labour_map` key directly to those event objects (confirmed design — the tool annotates other tools' events in place):
```json
{
  "lotId": "LOT-001",
  "date": "2026-09-14",
  "title": "🌾 B66DG1-Purple Haze#LOT-001, Harvest",
  "sourceTool": "CropLabourWizard",
  "taskType": "harvest",
  "labour_map": {
    "2026-09-14": [
      { "employee": "Jane Doe", "hours": 7.5 },
      { "temp": "Bob", "wage": 25, "hours": 4 }
    ]
  },
  "completed": true
}
```
- `labour_map` keys are ISO dates; each value records who worked that day and for how long. Regular employees reference roster names (wage resolved from the roster at report time); temp entries carry their own name + wage inline.
- **Hours logged on the floor:** DailyWizard adds entries to the same `labour_map` when staff log hours on a crop or equipment task. Those entries also carry `initials` (`{ name, strokes }`), `at` and `by`; a DailyWizard temp may have no `wage`. The Tasks tab lists them with a **✍️ signed** tag (and "no wage" for such a temp), and edits or deletes them like any other entry.
- Keys may fall **outside** the event's `[date, endDate]` range: when a single-day event turns into multi-day work, the task editor's "+ Add day" picker records extra days in `labour_map` without touching the event's dates (the task keeps sitting in its original due state until completed). Task hour/cost totals span **all** recorded days, not just the event range.
- `completed` is set when the task is marked finished from the task editor panel.

## Man-Hour Tracking

- **Cost per task-day** = Σ (hours × wage) across all entries in that day's labour map — regular employees use their roster wage, temps use their recorded wage.
- **Hours only without wages:** wages live in `Wages.json`, which only the office opens (root `CLAUDE.md` → "Split Database"). On a building device, or when no roster employee has a `wage`, the task editor's day / task totals show hours only — no $ figure built on a made-up default wage.
- **Day-to-day tracking:** each day's entries are recorded as work happens; previous days remain editable from the task editor.
- **Averages:** total hours per task ÷ plant count → average time per plant, enabling comparison across different size rooms.
- **Plant count source:** a `plantCount` field on the lot in SitkaTools (`lots.<LotID>.plantCount`) — set once at lot creation and shared by all tools. EmployeeWizard reads it for per-plant math; if a lot has no plant count, per-plant figures are unavailable for that lot (reports show totals only).

## BC Civic Holidays

**Not applicable.** EmployeeWizard is intentionally **not** holiday-aware — it does not check or notify about BC civic holidays. Holidays are already rendered on the main SitkaTools calendar, and this tool's dated events (time off) are user-initiated bookings where the user chooses the dates. **One exception:** the Reports tab takes BC civic holidays out of roster capacity and marks them on the room schedule Gantt and the demand chart (`rptHolidays`). Nothing is checked or notified.

## Relationship to SitkaTools

**Building devices** (root `CLAUDE.md` → "Building Device View") get only the **Tasks** tab, and its Active Lot list holds only that building's lots. Labour and completion are floor fields, saved in the building's own file. The roster, wages, time off, the Labour Report and the Reports tab are office work, so they're hidden there.

This tool is part of the SitkaGit suite. It operates as a standalone single-file HTML application with no communication to other tools. All shared state flows through the common JSON database file (`DB-YY-MM-DD.json`).

- Opens as a centered popup from `SitkaTools.html` at **half the main app's viewport width** and **83% of the viewport height**.
- Receives the DB via postMessage on open; sends updates back after every mutation (no localStorage, sessionStorage, IndexedDB, or cookies).
- The main app auto-refreshes all views when it receives a `sitkaGit_db_update`.
- **Live updates the other way:** SitkaTools posts `sitkaGit_db_update` whenever its DB changes (`WorkCopy.LIVE: true`). EmployeeWizard accepts it only from `window.opener` (or its own WorkCopy loader), replaces `DB.data`, applies the view and redraws its lists and calendars — the roster, work week / time-off calendar and task list, keeping the selected lot and task. No input or form field is reset, and it never calls `notifySitkaTools()` in response.

## Constraints

- Single `.html` file, no build step, no external dependencies
- Runs in browser sandbox (`file://` protocol)
- Vanilla HTML/CSS/JavaScript only
- No network calls of any kind
- No localStorage, sessionStorage, IndexedDB, or cookies — all cross-window state via postMessage
- Labour reports/graphs (Phase 5) must be hand-rolled (SVG/canvas) — no chart libraries
- The Reports tab may **read** every tool's data; it writes only `_EmployeeWizard.crops` / `.settings`

## Design Decisions (Confirmed)

1. **Work week layout:** Monday start (Mon–Sun columns), current week only — no week navigation in the work-week calendar.
2. **Employee identity:** Employees are keyed by name in `_EmployeeWizard.employees`; duplicate names are prevented (the name is the identity).
3. **Partial time off:** Hour-based entries — a book-off records specific hour ranges per day (`hoursOff`), so days can be partially booked off.
4. **Labour map storage:** `labour_map` and `completed` are written directly onto the Labour-wizard calendar event objects (in-place annotation). Tasks are identified by the event's stable `id` (`taskKey`), so a selection survives date or title changes made elsewhere; CropLabourWizard carries `labour_map` and `completed` over when it regenerates a schedule (root `CLAUDE.md` → "Event Annotations Survive Regeneration").
5. **Plant count source:** `plantCount` field on the lot in SitkaTools (`lots.<LotID>.plantCount`), shared by all tools; EmployeeWizard reads it for per-plant math.
6. **Holiday awareness:** None — this tool is not BC-civic-holiday-aware.
7. **Time-off event title:** `"🏖️ Time Off — <Name>"` confirmed as the calendar-event title format.
8. **Grown tasks:** single-day events that become multi-day work keep their original `date`/`endDate`; extra work days are recorded as additional `labour_map` keys via the "+ Add day" picker in the task editor (removable from the day row while they have no entries). Task totals include all recorded days.
9. **Global report mode:** the Active Lot selector's empty value (`''`) means *no lot / global scope*. When a lot is selected, the empty option is labeled "— No lot / Global report —" (otherwise "— Select a lot —"). In Phase 5, labour reports use this no-lot state to show cross-lot (global) figures instead of per-lot.
